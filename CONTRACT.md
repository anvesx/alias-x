# alias-x acceptance contract

Objective: exact Alias Bot parity, named alias-x; local real-Slack tests in a channel whose only human is the owner. No Cloudflare production deployment before local verification.

Reference: https://yippa.io/alias-bot/ inspected 2026-10-06. Public page establishes channel-local !aliases, channel-member targets, stable names with editable members, creation/deletion, visible alias/recipient replies, and creation records. Free plan: three aliases. Its FAQ buttons exposed no answers in the inspected browser. Original slash commands, permissions, reply placement, and exact UI are NOT VERIFIED. The following interface is provisional until original app behavior is observed; it is not evidence of exact parity.

Provisional /alias-x commands: help, list, show NAME, create NAME @members, set NAME @members, add NAME @members, remove NAME @members, delete NAME. Names normalize to lower case and allow ASCII letters, digits, _ and - (1..64). 1..100 distinct members per alias. Any current channel human member can manage channel aliases. Group references only recognize standalone !name outside inline/fenced code and links. Bot messages, edits, deletes, and messages outside the explicit test allowlist do not trigger mentions. Per the owner’s later customization, replies display only deduplicated actual channel-member handles (no alias label or notification-preference footer), in the triggering thread; no hidden broadcast mentions.

Storage: workspace/channel/name key; atomic create limit and mutations; revision check detects concurrent membership updates; event-id claim suppresses Slack retries. No message text retained. Store aliases, IDs, creation/update metadata, audit actions, and event claim states only. Recipient membership is checked again before posting. Fail closed when Slack membership cannot be read. Signed request freshness max 300s. Reject wrong workspace, unauthorized channels, malformed/oversized bodies. Do not accept secrets in committed files.

Required tests: full command lifecycle; three-alias limit; same-name channel/workspace isolation; channel member validation; unknown/empty/invalid/duplicate/Unicode/oversized inputs; repeated tokens and overlapping groups; membership changes/leavers; bot and edit suppression; concurrent updates/creates; request signature/timestamp/body tampering; Slack failures/rate limits; retry dedup; persistence across process restart; visible replies under the requested app identity; notification delivery as observable, not inferred from API success.

Real Slack evidence remains mandatory. A one-human channel cannot establish multi-human notification delivery. Exact-copy evidence also requires the original app or an authoritative complete specification. These are completion blockers, not scope reductions.

Slash-command replay contract: hash the exact signed request body; atomically claim once per workspace. Store the result before ephemeral delivery. A completed retry returns the cached result without another mutation or channel announcement. An interrupted processing claim returns an explicit uncertain-outcome message; never automatically repeat a possibly committed mutation.

Recovery contract: persist alias names and thread before event acknowledgement; a 120-second preparation lease and incrementing attempt fence stale senders. Membership pagination is bounded to 20 seconds total and eight seconds per request. A scheduled sweep retries known-safe preparation failures and known rate limits up to five attempts. Persist the sending boundary before external posting; ambiguous posting outcomes and expired send leases are uncertain and require manual thread inspection. Never blindly resend an uncertain notification. Retention is seven days for completed ledgers and 30 days for failure/uncertain/interrupted records. Existing legacy event claims suppress cross-migration retries.

Original parity evidence: official https://yippa.io/alias-bot/support confirms /alias and interactive Edit/Delete buttons. The current CLI alone fails exact UI parity. Original-app OAuth comparison has been prepared with displayed scopes; installation awaits explicit human permission because it is a separate third-party app.
