# alias-x acceptance contract

Objective: exact Alias Bot parity, named alias-x; local real-Slack tests in a channel whose only human is the owner. No Cloudflare production deployment before local verification.

Reference: https://yippa.io/alias-bot/ inspected 2026-10-06. Public page establishes channel-local !aliases, channel-member targets, stable names with editable members, creation/deletion, visible alias/recipient replies, and creation records. Free plan: three aliases. Its FAQ buttons exposed no answers in the inspected browser. Original slash commands, permissions, reply placement, and exact UI are NOT VERIFIED. The following interface is provisional until original app behavior is observed; it is not evidence of exact parity.

Provisional /alias-x commands: help, list [!AFTER_ALIAS], show NAME [PAGE], create NAME @members, set NAME @members, add NAME @members, remove NAME @members, delete NAME. Names normalize to lower case and allow ASCII letters, digits, _ and - (1..64). Per the owner's customization on 2026-10-08, there is no application-imposed alias-count or member-count quota. Any current channel human member can create as many aliases and add as many distinct current channel members as platform storage allows. Nonempty aliases, duplicate-name protection and optimistic update checks remain. List/show pages contain 100 aliases/200 members; signed requests are limited to 65,536 bytes and parsed commands to 12,000 characters, so members can be added incrementally. Group references only recognize standalone !name outside inline/fenced code and links. Bot messages, edits, deletes, and messages outside the explicit test allowlist do not trigger mentions. Replies display only deduplicated actual channel-member handles (no alias label or notification-preference footer), in the triggering thread; no hidden broadcast mentions. Native Slack notifications use recipients' Slack preferences.

Storage: workspace/channel/name key; atomic duplicate-name protection and mutations; revision check detects concurrent membership updates; event-id claim suppresses Slack retries. No message text retained. Store aliases, IDs, creation/update metadata, audit actions, event claim states and delivery recipient progress. Recipient membership is checked again before each resumed chunk. Fail closed when Slack membership cannot be read. Signed request freshness max 300s. Reject wrong workspace, unauthorized channels, malformed/oversized bodies. Do not accept secrets in committed files.

Required tests: full command lifecycle; one owner creating more than three aliases; membership growing beyond 100 through create/add/set/remove; complete list/show paging; same-name channel/workspace isolation; channel member validation; unknown/empty/invalid/duplicate/Unicode/oversized inputs; repeated tokens and overlapping groups; membership changes/leavers; bot and edit suppression; concurrent updates/creates; request signature/timestamp/body tampering; Slack failures/rate limits; retry dedup; large replies split without truncation or duplicates, including more than five successful chunks; persistence across process restart; visible replies under the requested app identity; notification delivery as observable, not inferred from API success.

Real Slack evidence remains mandatory. A one-human channel cannot establish multi-human notification delivery. Exact-copy evidence also requires the original app or an authoritative complete specification. These are completion blockers, not scope reductions.

Slash-command replay contract: hash the exact signed request body; atomically claim once per workspace. Store the result before ephemeral delivery. A completed retry returns the cached result without another mutation or channel announcement. An interrupted processing claim returns an explicit uncertain-outcome message; never automatically repeat a possibly committed mutation.

Recovery contract: persist alias names and thread before event acknowledgement; a 120-second preparation lease and incrementing attempt fence stale senders. Membership pagination has no page-count cap and is bounded to 20 seconds total and eight seconds per request. A scheduled sweep retries known-safe preparation failures and known rate limits up to five consecutive failures. Successful chunks reset failures only, preserving the fencing generation. Persist the recipient snapshot, next index and sending boundary before external posting. Messages contain at most 39,000 characters and whole handles; at most one chunk per job is posted per invocation, with further chunks continuing on scheduled sweeps. Known rate limits preserve progress. Ambiguous posting outcomes and expired send leases are uncertain and require manual thread inspection. Never blindly resend an uncertain notification. Retention is seven days for completed ledgers and 30 days for failure/uncertain/interrupted records. Migration 0004 preserves existing alias data, retry budgets and send states. Existing legacy event claims suppress cross-migration retries.

Original parity evidence: official https://yippa.io/alias-bot/support confirms /alias and interactive Edit/Delete buttons. The current CLI alone fails exact UI parity. Original-app OAuth comparison has been prepared with displayed scopes; installation awaits explicit human permission because it is a separate third-party app.
